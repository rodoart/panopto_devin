#### Alcance del Módulo: Monitor de Estabilidad y Calidad de Variables (MECV)

##### 1. Visión de Alto Nivel

El MECV es un orquestador de pruebas estadísticas que opera **sin triggers externos de producción**. Su única fuente de verdad es la disponibilidad de datos en tablas/parquets configurados. Cuando detecta que la información del periodo esperado ya existe, ejecuta automáticamente:

1. **Pruebas de calidad** por variable (`raw`, `input`, `transformed`, `score`, `target`).
2. **Pruebas de estabilidad** (PSI/CSI con bines fijos y con bines dinámicos).
3. **Evaluación de umbrales** (ámbar/rojo) y notificaciones.
4. **Persistencia de resultados** para tableros (Tableau).

**Regla de oro:** Cada modelo puede tener cualquier subconjunto de los 5 tipos de variable. El módulo no asume que todos existen.

####### A. Pruebas de Calidad (por variable, por tipo)
- **Completitud:** % de nulos.

##### 4. Flujo de Datos: Modo Entrenamiento vs. Producción

###### Modo Entrenamiento (Onboarding de Modelo)

```
1. Usuario/Analista inserta nuevo model_id en tablas de config
   ↓
2. DAG mecv_config_watcher detecta el cambio
   ↓
3. Lee las fuentes (tablas/parquets) definidas para el modelo
   ↓
4. Para cada variable presente (raw/input/transformed/score/target):
   a. Calcula bines canónicos (estratégicos o estadísticos)
   b. Persiste en csi_psi_table_d_t_d
   c. Registra umbrales en model_summary / tresholds_table
   ↓
5. Marca modelo como "active" y listo para monitoreo
```

###### Modo Producción (Monitoreo Continuo)

```
1. DAG mecv_production_runner se dispara según frecuencia del modelo
   ↓
2. Para cada variable configurada del modelo:
   a. Verifica si tabla/parquet tiene datos del information_date esperado
   b. Si NO: skip, log, reintenta próxima ejecución
   c. Si SÍ: ejecuta pruebas de calidad + estabilidad
   ↓
3. Persiste resultados en tablas de salida
   ↓
4. DAG mecv_alert_dispatcher evalúa umbrales y envía emails
   ↓
5. DAG mecv_output_validator verifica salidas y valida tableros
```

##### 1. Variables: Raw / Input / Transformed

###### 1.1 Calidad de Datos (Autónomas)

| Prueba | Fórmula / Definición | Interpretación | Umbral Típico |
|--------|---------------------|----------------|---------------|
| **Tasa de Nulos** (`null_rate`) | $\frac{\text{count}(X = \text{NULL})}{N}$ | Completitud. Si sube, el origen se está pudriendo. | Rojo: >10%, Ámbar: >5% |
| **Cardinalidad Relativa** (`cardinality_ratio`) | $\frac{\text{distinct}(X)}{N}$ | Explosión de categorías (one-hot bomb) o estancamiento (constante). | Rojo: >0.95 o =1 (constante) |
| **Tasa de Outliers** (`outlier_rate`) | IQR method: $X \notin [Q_1 - 1.5 \cdot \text{IQR}, Q_3 + 1.5 \cdot \text{IQR}]$ | El cuerpo del dato se está deformando. | Rojo: >5% vs baseline |
| **Rango Violado** (`range_violation`) | $\text{count}(X < \text{min}_{\text{dev}} \lor X > \text{max}_{\text{dev}})$ | Datos fuera de los límites del entrenamiento. | Rojo: >1% |
| **Zero/Blank Rate** (`zero_rate`) | $\frac{\text{count}(X = 0 \lor X = "")}{N}$ | Captura defaults no declarados como nulos. | Modelo-dependiente |

###### 1.2 Estabilidad Univariada (Autónomas)

| Prueba | Fórmula | Qué detecta | Notas |
|--------|---------|-------------|-------|
| **PSI Canónico** | $\text{PSI} = \sum_{i=1}^{k} (A_i - E_i) \cdot \ln\left(\frac{A_i}{E_i}\right)$ | Drift de distribución vs. baseline de desarrollo. Bines estáticos de `csi_psi_table`. | Si $E_i = 0$ o $A_i = 0$, usar corrección: $0 \to 0.0001$. |
| **PSI Dinámico** | Igual fórmula, pero bines calculados sobre ventana móvil de referencia (ej. últimos 90 días). | Drift vs. comportamiento reciente, no vs. origen. | Ventana configurable por `model_id`. |
| **CSI (Character Stability Index)** | $\text{CSI} = \sum_{i=1}^{k} (A_i - E_i) \cdot \frac{B_i}{E_i}$ donde $B_i$ es el WoE del bin de desarrollo. | Cambio en el poder predictivo de cada bin. | Requiere target de desarrollo para calcular WoE baseline. Si no hay, usar PSI como proxy. |
| **Kolmogorov-Smirnov** | $D = \sup_x |F_{\text{actual}}(x) - F_{\text{dev}}(x)|$ | Máxima divergencia entre CDFs. Más sensible a cambios en el centro que PSI. | p-value < 0.01 = rojo. |
| **Anderson-Darling** | $A^2 = N \int_{-\infty}^{\infty} \frac{(F_{\text{actual}} - F_{\text{dev}})^2}{F_{\text{dev}}(1-F_{\text{dev}})} dF_{\text{dev}}$ | Similar a KS pero pondera las colas. Crítico para riesgo crediticio. | Estadístico > umbral crítico según tabla. |
| **Wasserstein-1** (Earth Mover's) | $W_1 = \int_{-\infty}^{\infty} |F_{\text{actual}}(x) - F_{\text{dev}}(x)| dx$ | "Trabajo" necesario para transformar una distribución en otra. Intuitivo para no estadísticos. | Normalizado por rango de desarrollo. |

###### 1.3 Estabilidad Multivariada (Autónomas)

| Prueba | Definición | Qué detecta |
|--------|------------|-------------|
| **Correlación Drift** | $\Delta \rho_{ij} = |\rho_{ij}^{\text{actual}} - \rho_{ij}^{\text{dev}}|$ | Las relaciones entre variables se desmoronan. Importante para modelos lineales o con regularización L2. | Ámbar: >0.15, Rojo: >0.30 |
| **Covarianza Generalizada** | $\|\Sigma_{\text{actual}} - \Sigma_{\text{dev}}\|_F$ (norma de Frobenius) | Cambio en la estructura de covarianza global. | Normalizado por $\|\Sigma_{\text{dev}}\|_F$. |

| Prueba | Definición | Interpretación |
|--------|------------|----------------|
| **Rango del Score** | $\min(S), \max(S), \text{percentiles}(5, 25, 50, 75, 95)$ | ¿El score sigue viviendo donde debería? Si un score de probabilidad empieza a salir de [0,1], algo está roto en la pipeline. |
| **Concentración del Score** (Gini del score consigo mismo) | $G = \frac{2 \sum_{i=1}^{N} i \cdot S_{(i)}}{N \sum S_{(i)}} - \frac{N+1}{N}$ | Un score perfectamente uniforme tiene Gini=0. Un score que se concentra en un punto tiene Gini→1. **No es el Gini del modelo** (eso requiere target). Es la desigualdad interna del score. Si cambia drásticamente, la escala se descompuso. |
| **Entropía del Score** (discretizado) | $H(S) = -\sum_{b} p_b \ln(p_b)$ | ¿El score sigue discriminando o se ha vuelto perezoso y se amontona? Caída de entropía = pérdida de resolución. |
| **Tasa de Score Nulo** | $\frac{\text{count}(S = \text{NULL})}{N}$ | Si el modelo no pudo producir score para alguien, es un fallo de producción, no de datos. |

###### 2.2 Estabilidad del Score (Autónomas)

| Prueba | Fórmula / Método | Notas |
|--------|------------------|-------|
| **PSI del Score** | PSI canónico vs. baseline de desarrollo. | El score es una variable más, pero con peso estratégico. Umbral más estricto que variables comunes: ámbar 0.05, rojo 0.10. |
| **PSI Dinámico del Score** | Ventana móvil. | Detecta degradación gradual que el canónico no ve porque el baseline es antiguo. |
| **KS del Score vs. Desarrollo** | $D = \sup |F_{\text{actual}}(S) - F_{\text{dev}}(S)|$ | Si el score se ha vuelto más/menos extremo. |
| **Estabilidad de Percentiles Clave** | $\Delta P_{10}, \Delta P_{90}$ vs. baseline | El score puede mantener su PSI bajo pero las colas pueden migrar. Crítico para asignación de capital. |

###### 2.3 Pruebas con Umbral (Cut-off) — Autónomas

Aquí es donde tu requerimiento se vuelve interesante. El `cut_off_probability` de `model_summary_csi_psi_d_t_d` permite definir positivos/negativos **sin necesidad de target real**.

| Prueba | Definición | Interpretación |
|--------|------------|----------------|
| **Tasa de Aprobación / Positivos** | $\tau = \frac{\text{count}(S > \text{cutoff})}{N}$ | ¿Qué porcentaje del universo está siendo clasificado como "bueno" o "malo"? Si el cutoff es 0.35 y de repente apruebas al 90%, el mundo cambió o el modelo se descompuso. |
| **PSI Condicional: Aprobados vs. Rechazados** | $\text{PSI}(S_{\text{approved}}^{\text{actual}} \| S_{\text{approved}}^{\text{dev}})$ | Estabilidad de la distribución **dentro** de los que pasan el corte. Puedes tener PSI global sano pero los aprobados ser ahora todos de un tipo. |
| **Momento del Corte** | $\frac{\text{mean}(S \mid S > \text{cutoff})}{\text{mean}(S \mid S \leq \text{cutoff})}$ | Razón de concentración. Si se desploma, el corte ya no separa mundos. |
| **Score Medio por Decil** | $\bar{S}_d$ para $d=1...10$ | Perfil del score. Si los deciles se aplastan o invierten, hay rotura de monotonicidad. |

> **⚠️ Agujero lógico que debes cerrar:** ¿El cutoff es estático (el del entrenamiento) o se actualiza? Si el negocio mueve el cutoff manualmente, tu prueba de "tasa de aprobación" dejará de ser una prueba del modelo y será una prueba del negocio. Decide: ¿monitoreas el modelo con cutoff fijo, o monitoreas el negocio con cutoff variable? No puedes hacer ambos en la misma métrica sin desglosar.

##### 3. Target: El Testigo Tardío

El target llega tarde (si es que llega). Para modelos de originación, puede tardar 12-24 meses. Para modelos de comportamiento, quizá 1-3 meses. Por tanto, las pruebas de target deben ser **retroactivas**: cuando el target llega, se ejecutan sobre los scores históricos de esos periodos.

###### 3.1 Calidad del Target (Autónomas, cuando existe)

| Prueba | Definición | Interpretación |
|--------|------------|----------------|
| **Tasa de Evento** | $\bar{Y} = \frac{\sum Y_i}{N}$ | ¿El mundo sigue teniendo la misma morosidad/fracaso que cuando entrenaste? |
| **PSI del Target** | PSI de $Y$ vs. baseline de desarrollo. | El target es la variable más importante para estabilidad. Si la tasa de evento se mueve, todo el modelo necesita recalibración. |
| **Completitud del Target** | % de registros con score que ya tienen target observado | Indica madurez de la muestra. No es una prueba del modelo, pero es una prueba de la viabilidad de las pruebas conjugadas. |

###### 3.2 Desempeño del Modelo (Conjugadas: Score + Target)

| Prueba | Fórmula | Qué mide | Condición de activación |
|--------|---------|----------|------------------------|
| **AUC-ROC** | $\int_0^1 \text{TPR}(t) \, d\text{FPR}(t)$ | Capacidad discriminativa global. | `score` y `target` existen para el mismo `information_date`. |
| **Gini (Coef. de Correlación)** | $\text{Gini} = 2 \cdot \text{AUC} - 1$ | Estandar bancario. Gini < 0.30 suele ser rojo en crédito. | Mismo que AUC. |
| **KS (Score entre Target=1 y Target=0)** | $D = \sup |F_1(S) - F_0(S)|$ | Máxima separación entre buenos y malos. Más robusto que AUC ante desbalance. | Mismo que AUC. |
| **Brier Score** | $\text{BS} = \frac{1}{N} \sum (S_i - Y_i)^2$ | Calibración: ¿el score de 0.30 realmente predice 30% de eventos? | Mismo que AUC. |
| **Log-Loss** | $-\frac{1}{N} \sum [Y_i \ln(S_i) + (1-Y_i)\ln(1-S_i)]$ | Penaliza más las predicciones confiadas y equivocadas. | Mismo que AUC. |
| **Matriz de Confusión (con cutoff)** | TP, FP, TN, FN dado `cut_off_probability` | Desempeño operativo. | Mismo que AUC. |
| **Precision / Recall / F1** | Derivados de la matriz. | Balance según estrategia de negocio. | Mismo que AUC. |
| **Lift en Deciles** | $\text{Lift}_d = \frac{\bar{Y}_d}{\bar{Y}}$ | Poder de ordenamiento por decil. Si el decil 10 no tiene 5x la tasa de evento del promedio, el modelo se descompuso. | Mismo que AUC. |
| **Calibration Curve** | $\bar{Y}$ vs. $\bar{S}$ por bins de score | Si el modelo predice 0.20 pero el evento ocurre al 0.35, está subestimando el riesgo. | Mismo que AUC. |

###### 3.3 Estabilidad del Desempeño (Conjugadas)

| Prueba | Definición | Qué detecta |
|--------|------------|-------------|
| **Variación de Gini** | $\Delta \text{Gini} = \text{Gini}_{\text{actual}} - \text{Gini}_{\text{dev}}$ | Degradación del poder predictivo. Ámbar: caída > 5%, Rojo: > 10%. |
| **Variación de KS** | $\Delta \text{KS} = \text{KS}_{\text{actual}} - \text{KS}_{\text{dev}}$ | Similar al anterior, pero más sensible a colas. |
| **PSI del Score entre Target=1** | PSI de $S \mid Y=1$ vs. baseline | ¿Los malos se ven diferentes? El modelo puede seguir discriminando pero los malos nuevos son de otra especie. |
| **PSI del Score entre Target=0** | PSI de $S \mid Y=0$ vs. baseline | ¿Los buenos se ven diferentes? |

##### 3. Sistema de Alertas Agregadas: "El Peso del Amarillo"

No queremos un email por cada métrica que se pasa de 0.001 en el PSI. Queremos una **fotografía del modelo** por tipo de variable.

###### 3.1 Algoritmo de Agregación

Para cada combinación `(model_id, information_date, var_type)` donde `var_type ∈ {raw, input, transformed, score}`:

1. **Contar métricas aplicables** (las que no fueron `NOT_APPLICABLE` por falta de datos o tipo de dato).
   - $N_{\text{total}}$ = total de métricas que corrieron.

2. **Contar alertas**:
   - $C_{\text{ambar}}$ = métricas en ámbar.
   - $C_{\text{rojo}}$ = métricas en rojo.

3. **Calcular equivalente amarillo**:
   $$E = C_{\text{ambar}} + C_{\text{rojo}} \times W$$
   donde $W$ = `red_equivalent` (de `alert_policy` o default 3).

4. **Calcular ratio de estrés**:
   $$R = \frac{E}{N_{\text{total}} \times W}$$

   *(Normalizado: si todo fuera rojo, $R=1$; si todo ambar, $R=1/W$; si verde, $R=0$)*

5. **Determinar status agregado**:
   - Si $R \geq$ `alert_red_pct` → **ROJO** agregado.
   - Si $R \geq$ `alert_ambar_pct` → **ÁMBAR** agregado.
   - Si no → **VERDE**.

###### 3.2 Ejemplo Vivo

Modelo `1079_cta_lvl`. Tipo `input`. 10 variables input, cada una con 3 métricas (null, psi_dyn, ks) = 30 métricas totales.

Configuración: `red_equivalent=3`, `alert_ambar_pct=0.50`, `alert_red_pct=0.30`.

**Escenario A:** 6 métricas ámbar, 2 rojas.
- $E = 6 + 2\times3 = 12$
- $R = 12 / (30 \times 3) = 12/90 = 0.133$
- Resultado: **VERDE** (0.133 < 0.50)

**Escenario B:** 10 métricas ámbar, 3 rojas.
- $E = 10 + 9 = 19$
- $R = 19/90 = 0.211$
- Resultado: **VERDE** (aún no llega a 0.30)

**Escenario C:** 5 ámbar, 6 rojas.
- $E = 5 + 18 = 23$
- $R = 23/90 = 0.256$
- Resultado: **ÁMBAR** (pasa 0.30? No, 0.256 < 0.30. Sigue verde. Espera...)

Corrijo: en el Escenario C, 0.256 < 0.30, sigue siendo verde. Necesito un ejemplo que cruce.

**Escenario D:** 0 ámbar, 9 rojas.
- $E = 0 + 27 = 27$
- $R = 27/90 = 0.30$
- Resultado: **ÁMBAR** justo en el límite.

**Escenario E:** 0 ámbar, 10 rojas.
- $E = 30$
- $R = 30/90 = 0.333$
- Resultado: **ÁMBAR** (0.333 ≥ 0.30, pero < 0.50)

**Escenario F:** 0 ámbar, 15 rojas.
- $E = 45$
- $R = 45/90 = 0.50$
- Resultado: **ROJO** justo en el límite.

Esto funciona: tolera mucho ruido amarillo (hasta 50% del máximo posible), pero los rojos pesan 3x y aceleran la alerta.

##### 4. Auto-Configuración: Modo Entrenamiento Detallado

Cuando se añade un nuevo modelo, el DAG `mecv_config_watcher` ejecuta:

###### Paso 1: Inventario de Variables
Lee las tablas/parquets definidos para el modelo. Detecta qué columnas existen y clasifica:
- Numéricas: `dtype` en (float, int, double).
- Categóricas: `dtype` en (string, varchar, object) o cardinalidad < 20.
- Score: identificado por nombre configurado o por metadata.
- Target: identificado por nombre configurado.

###### Paso 2: Bines Canónicos (Congelados para CSI)

**Numéricas:**
- Si la variable tiene ≤10 valores únicos: cada valor es un bin (categórico forzado).
- Si tiene >10: calcular 10 bins por **quantiles** de la muestra de desarrollo. O usar árbol de decisión simple (1 nivel) para cortes que maximicen separación del target (si target existe en desarrollo).
- Persistir en `csi_psi_table_d_t_d` con `bin_type='NUMERIC'`.

**Categóricas:**
- Agrupar por frecuencia: top 9 categorías + 1 bin "OTROS".
- Calcular WoE de cada categoría usando el target de desarrollo (si existe): $\text{WoE}_c = \ln\frac{P(X=c \mid Y=0)}{P(X=c \mid Y=1)}$.
- Persistir en `csi_psi_table_d_t_d` con `bin_type='CATEGORICAL'`, `category_value` = valor o "OTROS".

**Score (probabilidad):**
- 10 bins de ancho fijo: [0,0.1), [0.1,0.2), ..., [0.9,1.0].
- O 10 bins de deciles si el negocio prefiere. Decisión: **deciles** para score, porque la probabilidad no es lineal en importancia.

###### Paso 3: Umbrales de Calidad

Para cada métrica de calidad, calcular:
- `baseline_value` = valor en desarrollo.
- `baseline_std` = desviación estándar (si hay múltiples muestras) o estimado por bootstrap.
- `threshold_ambar` = `baseline + 2*std` (o heurística si no hay std).
- `threshold_red` = `baseline + 4*std` (o heurística).

Persistir en `metric_threshold_auto_d_t_d`.

###### Paso 4: Ventana Dinámica

Heurística automática según frecuencia del modelo (configurada al dar de alta el modelo):

| Frecuencia | Ventana Default |
|------------|-----------------|
| Diaria | 4 semanas |
| Semanal | 12 semanas |
| Mensual | 6 meses |

El usuario puede sobrescribir en `model_summary`. Si no hay nada, aplica default y persiste.

###### Paso 5: Política de Alertas

Insertar filas en `alert_policy_d_t_d` con defaults:
- `raw`: `red_equivalent=3`, `alert_ambar_pct=0.60`, `alert_red_pct=0.40` (más permisivo, son datos crudos).
- `input`: `red_equivalent=3`, `alert_ambar_pct=0.50`, `alert_red_pct=0.30`.
- `transformed`: `red_equivalent=3`, `alert_ambar_pct=0.50`, `alert_red_pct=0.30`.
- `score`: tomar de `model_summary` (`score_alert_ambar_pct`, etc.). Si no hay: `alert_ambar_pct=0.30`, `alert_red_pct=0.15`, `red_equivalent=2` (más estricto).

##### 2. Drift Categórico: El Top N como Frontera

Tu idea es aguda. Si una categoría entra o sale del ranking, no es solo un cambio de frecuencia: es un **cambio de semántica**. El modelo entrenó con un mundo donde "CDMX" representaba el 40% de los datos; si de repente "Guadalajara" entra al top 5 con el 25%, el modelo está leyendo un atlas distinto.

| `critical_top_k` | int | Umbral para alerta **roja** si entra/sale del top K. Default: 5. |
| `process_date` | date | |
| `process_date` | date | |

###### Nueva Métrica: `category_composition_drift`

Para cada variable categórica, en cada ejecución:

1. **Calcular ranking actual** por frecuencia: $R_{\text{actual}}(c) = \text{rank}$ de la categoría $c$.
2. **Comparar contra baseline** (último modo entrenamiento):
   - **Categoría nueva en top `critical_top_k`:** Nunca estuvo en el top K de desarrollo y ahora está. → **ROJO**.
   - **Categoría que sale del top `critical_top_k`:** Estaba en el top K de desarrollo y ya no está. → **ROJO**.
   - **Categoría nueva en top `top_n_threshold`:** Nunca estuvo en el top N y ahora está. → **ÁMBAR**.
   - **Categoría que sale del top `top_n_threshold`:** Estaba en el top N y ya no está. → **ÁMBAR**.
   - **Categoría que permanece en top N pero cambia de ranking significativamente:** Cambio de >5 posiciones. → **ÁMBAR**.

3. **Métrica cuantitativa:** `category_composition_drift` = proporción de categorías en top N que son diferentes al baseline (índice de Jaccard sobre el conjunto de categorías):
   $$J = \frac{| \text{Top}_N^{\text{actual}} \cap \text{Top}_N^{\text{dev}} |}{| \text{Top}_N^{\text{actual}} \cup \text{Top}_N^{\text{dev}} |}$$
   - $J < 0.9$ → Ámbar.
   - $J < 0.7$ → Rojo.

###### Actualización de la Tabla `csi_psi_table_d_t_d` para Categóricas

Cuando el modo entrenamiento corre:

- Si la variable tiene ≤ `top_n_threshold` categorías: cada categoría es un bin propio.

##### 3. Watcher de Configuración: Entrenamiento como Mutación, no como Nacimiento

Tu tercer punto cambia la naturaleza del `mecv_config_watcher`. Ya no es un partero que solo atiende nacimientos (`model_id` nuevo). Es un **vigía de mutaciones**.

###### Lógica del Watcher Actualizado

El DAG corre cada 15 minutos (o cada hora, según criticidad):

```python
#### Pseudocódigo del watcher
def detect_config_changes():
    # 1. Leer última partición de cada tabla de config (patrón LATEST_PARTITION)
    current_config = load_latest_partitions()
    
    # 2. Calcular fingerprint (hash MD5 de contenido ordenado) por modelo
    current_hashes = {
        model_id: hash(config_rows) 
        for model_id, config_rows in current_config.groupby('model_id')
    }
    
    # 3. Leer hashes almacenados en tabla de estado: config_fingerprint_d_t_d
    stored_hashes = load_stored_fingerprints()
    
    # 4. Comparar
    for model_id, current_hash in current_hashes.items():
        if model_id not in stored_hashes:
            trigger_training(model_id, reason="NEW_MODEL")
        elif current_hash != stored_hashes[model_id]:
            trigger_training(model_id, reason="CONFIG_CHANGED")
            
    # 5. Persistir nuevos hashes
    persist_fingerprints(current_hashes)
```

|-------|------|-------------|
| `model_id` | string | |

###### ¿Qué pasa cuando hay cambio?

| Escenario | Acción del Modo Entrenamiento |
|-----------|------------------------------|
| Nuevo `model_id` | Inventario completo, cálculo de bines, umbrales, políticas. Marca como `active`. |
| Nuevo `process_date` en `model_summary` (mismo model_id) | Relee cutoff, umbrales, ventana. Recalcula solo lo que cambió. Si el cutoff cambia, regenera bines de score. |

| Cambio en `category_policy` | Recalcula categorías baseline y ranking. |

> **F3 en acción:** El sistema muta, pero deja huella. Cada reentrenamiento genera una entrada en `mecv_execution_log` con `reason='CONFIG_CHANGED'`. Nunca se sobrescribe el pasado; solo se añade una nueva partición.

###### ¿Qué pasa con los huecos?

| Situación | Comportamiento |
|-----------|---------------|

```python
def get_expected_information_date(model_id, run_date):
    config = load_latest_partition(model_summary, model_id)
    freq = config.frequency  # 'daily', 'weekly', 'monthly', 'business_daily'
    
    if freq == 'business_daily':
        # Último día hábil anterior o igual a run_date
        expected_date = spark.sql(f"""
            SELECT MAX(calendar_date) 
            FROM banamex_calendar_d_t_d 
            WHERE calendar_date <= '{run_date}' AND is_business_day = true
        """).collect()[0][0]
    elif freq == 'daily':
        expected_date = run_date
    elif freq == 'weekly':
        expected_date = run_date - 7 days  # o el último día hábil de la semana anterior
    elif freq == 'monthly':
        expected_date = last_day_of_previous_month(run_date)
    
    return expected_date
```

#### Documento de Alcance Final: MECV (Módulo de Estabilidad y Calidad de Variables)

##### 1. Filosofía Operativa (3 Reglas Inquebrantables)

1. **LATEST_PARTITION o muerte.** Toda lectura de config lee la última partición del modelo. No hay excepciones, no hay joins con el pasado, no hay sorpresas.
2. **Parcheo selectivo.** El modo entrenamiento solo recalcula lo que mutó. Si una variable no cambió, sus bines canónicos y su baseline permanecen congelados, inmunes al tiempo.
3. **SKIP = ROJO.** Si los datos no llegan el día que debieron llegar, la alerta es crítica desde el primer día y se repite cada día hasta que lleguen o alguien apague el modelo.

##### 3. Motor de Pruebas: Catálogo Final

###### 3.1 Variables (raw, input, transformed)

| Métrica | Fórmula | Tipo de Dato | Umbral |
|---------|---------|--------------|--------|
| `null_rate` | nulos / N | Todas | Auto: baseline + 2σ (ámbar), +4σ (rojo). Sin σ: 5% / 10%. |
| `cardinality_ratio` | distinct / N | Todas | Rojo: >0.95 o =1 |
| `outlier_rate` | IQR | Numéricas | Auto: baseline + 3% / 6% |
| `dominant_category_rate` | max(freq) / N | Categóricas | Rojo: >90% |
| `category_composition_drift` | Jaccard(top_N) | Categóricas | Ámbar: J<0.9. Rojo: J<0.7. |
| `top_k_entry_exit` | Entrada/salida del top K | Categóricas | Rojo si entra/sale del critical_top_k |
| `psi_canonical` | Σ(A-E)·ln(A/E) | Todas | De `tresholds_table` o default 0.1/0.2 |
| `psi_dynamic` | PSI vs ventana móvil | Todas | De `tresholds_table` o default 0.1/0.2 |
| `ks_vs_dev` | sup\|F_actual - F_dev\| | Numéricas | p<0.01 rojo |
| `correlation_drift` | max Δρ | Input (≥2 vars) | Ámbar: >0.15. Rojo: >0.30. |

###### 3.2 Score (Autónomo)

| Métrica | Fórmula | Umbral |
|---------|---------|--------|
| `range_violation` | count(S∉[0,1]) / N | Rojo: >0% |
| `null_rate` | nulos / N | Rojo: >0% |
| `entropy` | -Σ p_b ln(p_b) sobre 10 bins | Ámbar: caída >15%. Rojo: >30%. |
| `concentration_gini` | Gini(S) | Ámbar: cambio >10%. Rojo: >20%. |
| `psi_canonical` | PSI vs baseline | Score: ámbar 0.05, rojo 0.10 |
| `psi_dynamic` | PSI vs ventana | Igual |
| `ks_vs_dev` | sup\|F_actual - F_dev\| | p<0.01 rojo |

| `approval_rate` | count(S>cutoff) / N | Ámbar: desvío >10% baseline. Rojo: >20%. |
| `psi_approved` | PSI(S \| S>cutoff) | vs baseline aprobados |
| `psi_rejected` | PSI(S \| S≤cutoff) | vs baseline rechazados |

##### 4. Sistema de Alertas Agregadas

###### Algoritmo (por model_id + information_date + var_type)

```
E = count_ambar + count_red × red_equivalent
R = E / (total_metrics × red_equivalent)

Si R ≥ alert_red_pct     → ROJO agregado
Si R ≥ alert_ambar_pct   → ÁMBAR agregado
Si no                    → VERDE
```

###### Política por Defecto

| var_type | red_equivalent | alert_ambar_pct | alert_red_pct |
|----------|---------------|-----------------|---------------|
| raw | 3 | 0.60 | 0.40 |
| input | 3 | 0.50 | 0.30 |
| transformed | 3 | 0.50 | 0.30 |
| score | 2 | 0.30 | 0.15 |

###### Email Consolidado por Modelo

Un solo email por modelo con:

- **Score:** Status agregado + todas las métricas en rojo (siempre listadas).
- **Input/Transformed:** Status agregado + top 3 rojas.
- **Raw:** Solo si agregado es ámbar/rojo.
- **Target:** Gini actual vs baseline, Brier, Lift (si existe).
- **Datos faltantes:** Si `status = MISSING_DATA`, banner rojo con texto: "El modelo no recibió datos para information_date = X. Días consecutivos sin datos: N."
- **Acción sugerida:** Texto automático según la métrica roja dominante.

##### 5. Orquestación: Los 4 DAGs

###### DAG 1: `mecv_config_watcher`
**Frecuencia:** Cada 30 minutos (o cada hora en horario laboral).

**Tareas:**

1. `sync_calendar`: Hive → Postgres. `INSERT INTO banamex_calendar_sync_d SELECT * FROM hive.banamex_calendar WHERE calendar_date >= CURRENT_DATE - 30`.
2. `detect_config_changes`: Lee LATEST_PARTITION de cada tabla de config. Compara contra `config_changelog`. Si hay diferencia:
   - Inserta en `config_changelog`.
   - Lanza `trigger_training`.
3. `mode_training`: Para cada modelo con cambio:
   - Inventario de variables desde fuentes configuradas.
   - Para variables nuevas/modificadas: calcula bines canónicos, WoE, umbrales auto, baseline de categorías.
   - Persiste en `csi_psi_table` (nueva partición), `category_baseline_rank`, `metric_threshold_auto`.
   - Variables existentes sin cambio: se copian con `process_date` actualizadas (parcheo selectivo).
4. `validate_training`: Verifica que las nuevas particiones sean legibles. Si falla, marca `triggered_retraining = false` en changelog.

###### DAG 2: `mecv_production_runner`
**Frecuencia:** Diaria (o según frecuencia del modelo).

**Tareas:**

1. `check_business_day`: Lee `banamex_calendar_sync_d`. Si no es día hábil y el modelo es `business_daily`, lanza `AirflowSkipException`.
2. `compute_expected_date`: Según frecuencia y calendario.
3. `check_data_availability`: Para cada variable del modelo, verifica si la fuente tiene datos para `information_date` esperado.
   - Si **NO**: Inserta en `mecv_execution_log` con `status = MISSING_DATA`, `reason = SCHEDULED`. Lanza alerta crítica. Termina ejecución para este modelo.
   - Si **SÍ**: Continúa.
4. `run_quality_tests`: Ejecuta métricas de calidad (Spark).
5. `run_stability_tests`: Ejecuta PSI/CSI/KS (Spark).
6. `run_score_tests`: Si hay score, ejecuta métricas autónomas + con cutoff.
7. `run_conjugate_tests`: Si hay target para el mismo periodo, ejecuta AUC/Gini/Brier/etc.
8. `persist_results`: Escribe `mecv_metric_result` y `mecv_alert_aggregate`.
9. `log_success`: Inserta en `mecv_execution_log` con `status = SUCCESS` o `PARTIAL`.

###### DAG 3: `mecv_alert_dispatcher`
**Frecuencia:** Diaria, dependiente de `mecv_production_runner`.

**Tareas:**

1. `read_daily_results`: Lee `mecv_alert_aggregate` del día.
2. `build_email_content`: Agrupa por modelo. Aplica plantilla.
3. `send_emails`: Envía vía SMTP. Marca `alert_sent = true`.
4. `handle_missing_data`: Lee `mecv_execution_log` donde `status = MISSING_DATA` y no se ha alertado hoy. Envía email crítico separado.

###### DAG 4: `mecv_output_validator`
**Frecuencia:** Diaria, post-dispatcher.

**Tareas:**

1. `validate_output_tables`: Verifica que `mecv_metric_result` y `mecv_alert_aggregate` tengan datos del día.
2. `trigger_tableau_refresh**: Si las tablas están sanas, llama a la API de Tableau (o actualiza una tabla de control que Tableau monitorea).
3. `log_refresh`: Registra éxito/fracaso del refresco.

```
DÍA 0: Analista sube nuevo model_id a model_summary
    ↓

    ↓
```

##### 2. Lógica de Notificación (DAG 3: Alert Dispatcher)

###### Algoritmo de Construcción de Destinatarios

Para cada modelo con alerta activa (ámbar, rojo, o missing data):

```
destinatarios = Set()

#### 1. Lista roja global (siempre, para todo)
para cada email en red_alert_list_d donde is_active=true:
    destinatarios.add(email)

#### 2. Contactos específicos del modelo (última partición de model_contact)
contactos = SELECT * FROM model_contact WHERE model_id = X AND process_date = MAX

para cada contacto:
    si aggregate_status = 'RED' y contacto.notify_on_red = true:
        destinatarios.add(contacto.email)
    si aggregate_status = 'AMBAR' y contacto.notify_on_ambar = true:
        destinatarios.add(contacto.email)
    si execution_status = 'MISSING_DATA' y contacto.notify_on_missing = true:
        destinatarios.add(contacto.email)

#### 3. Enviar un solo email por modelo con todos los destinatarios en TO o BCC
#### (recomendado BCC para no exponer listas entre sí)
```

###### Tipos de Email

| Tipo | Trigger | Destinatarios | Contenido |
|------|---------|---------------|-----------|
| **Crítico - Datos Faltantes** | `execution_log.status = MISSING_DATA` | Lista roja + contactos con `notify_on_missing=true` | Banner rojo. Modelo, fecha esperada, días consecutivos sin datos, fuentes declaradas que no llegaron. |
| **Crítico - Rojo Agregado** | `alert_aggregate.aggregate_status = 'RED'` | Lista roja + contactos con `notify_on_red=true` | Métricas en rojo, top 3 variables afectadas, acción sugerida. |
| **Advertencia - Ámbar Agregado** | `alert_aggregate.aggregate_status = 'AMBAR'` | Solo contactos con `notify_on_ambar=true` | (Lista roja NO entra aquí. Un ámbar no es incendio.) |
| **Resumen Verde** | Opcional, configurable | Solo `OWNER` | "Todo bien. Nada que hacer." |

> **Nota sobre la no-exclusividad:** Un email puede estar en `red_alert_list` Y en `model_contact` del modelo 1079. Recibe el email una sola vez (el `Set()` se encarga). No hay duplicados.

##### 4. Modo Entrenamiento: Flujo Detallado con Fuente Explícita

Cuando `mecv_config_watcher` detecta un cambio y lanza el modo entrenamiento:

###### Paso 1: Validación de Metadata
```python
for each row in variable_metadata_d_t_d where model_id = X:
    assert source_table existe en Hive/FS
    assert source_column existe en el schema de source_table
    assert information_date_column existe
```

Si falla cualquier `assert`, el entrenamiento se aborta y se escribe en `config_changelog`:
`triggered_retraining = false`, `error_message = "Variable X no encontrada en Y"`.

###### Paso 2: Cálculo de Bines Canónicos
- Lee los datos históricos de cada fuente declarada (últimos N días configurables, default 90).
- Aplica la lógica de binning según `data_type` y `category_policy`.
- Persiste en `csi_psi_table_d_t_d` con `process_date = hoy`.

###### Paso 3: Cálculo de Baselines de Categoría
- Para cada variable categórica, calcula ranking y frecuencia.
- Persiste en `category_baseline_rank_d_t_d`.

###### Paso 4: Cálculo de Umbrales Automáticos
- Para cada métrica de calidad, calcula `baseline_value` y `baseline_std` sobre el periodo de desarrollo.
- Persiste en `metric_threshold_auto_d_t_d`.

###### Paso 5: Fingerprint y Changelog
- Inserta en `config_changelog` con `triggered_retraining = true`.
- El modelo queda listo para producción.

---

##### 5. Modo Producción: Flujo Detallado con Datos Faltantes = Crítico

Cuando `mecv_production_runner` se dispara:

###### Paso 1: Calendario
- Lee `banamex_calendar_sync_d` (Postgres local).
- Si hoy no es hábil y el modelo es `business_daily`, skip silencioso. Sin alerta.

###### Paso 2: Fecha Esperada
```python
expected_info_date = calcular_según_frecuencia_y_calendario(model_id, hoy)
```

###### Paso 3: Verificación de Fuentes (UNA POR UNA)

Para cada variable en `variable_metadata_d_t_d`:

```python
fuente = variable.source_table + "." + variable.source_schema
columna = variable.source_column
fecha_col = variable.information_date_column

datos = spark.read.format(...).load(fuente).filter(col(fecha_col) == expected_info_date)

if datos.count() == 0:
    variables_faltantes.append(variable)
```

**Si `variables_faltantes` no está vacío:**
- NO se ejecuta ninguna prueba.
- Se inserta en `mecv_execution_log`:
  - `status = 'MISSING_DATA'`
  - `error_message = "Faltan variables: [lista]"`
  - `reason = 'SCHEDULED'`
- Se inserta en `mecv_alert_aggregate` un registro especial:
  - `var_type = 'SYSTEM'`
  - `aggregate_status = 'RED'`
  - `total_metrics = 0`, `count_red = 1` (forzado)
- El DAG 3 (`alert_dispatcher`) leerá esto y enviará email crítico.
- El modelo se reintenta mañana (mismo flujo).

**Si todas las variables tienen datos:**
- Continúa a pruebas.

###### Paso 4: Ejecución de Pruebas

Por cada variable, según su `var_type` y `data_type`, ejecuta solo las métricas aplicables (ver Catálogo Sección 3 del documento anterior). Las no aplicables se registran como `NOT_APPLICABLE`, no se omiten.

###### Paso 5: Agregación y Alertas

Calcula `stress_ratio` y `aggregate_status` por `var_type`. Persiste en `mecv_alert_aggregate`.

###### Paso 6: Log de Ejecución

`status = 'SUCCESS'` si todo corrió, `'PARTIAL'` si alguna métrica falló internamente pero el resto funcionó.

##### 8. Decisiones de Diseño Congeladas

| Decisión | Valor | Razón |
|----------|-------|-------|
| Lectura de config | `LATEST_PARTITION` por `model_id` | Evita mezclar configuraciones de diferentes épocas |
| Binning canónico | Congelado en entrenamiento, parcheo selectivo | Trazabilidad + eficiencia |
| Binning dinámico | Recalculado en cada ejecución sobre ventana del modelo | Detecta degradación gradual |
| Ventana dinámica | Configurable por modelo (`window_value` + `window_unit`) | Flexibilidad |
| Categóricas | Top N (default 50) + OTROS, critical top K (default 5) | Balance entre granularidad y estabilidad |
| Alertas agregadas | `stress_ratio` con `red_equivalent` | Tolerancia al ruido amarillo, peso al rojo |
| Datos faltantes | `MISSING_DATA` = alerta crítica desde día 1 | No se asume que "mañana llega" |
| Notificación | Lista roja global + contactos por modelo | Bomberos universales + dueños específicos |
| Fuente de datos | Declarada explícitamente en `variable_metadata` | Nunca adivinar, nunca ambigüedad |
| Tableau | Tablas en Hive, lectura pasiva | Desacoplamiento, sin APIs por ahora |

##### Decisiones de Diseño en los DDLs

###### 1. Particionamiento: `information_date` como STRING, no DATE

Sé que suena herejía. Pero en Hive tradicional, particionar por `DATE` es un dolor de cabeza cuando haces `INSERT OVERWRITE` dinámico desde Spark. El formato `'yyyy-MM-dd'` como STRING es la moneda de cambio en bancos legacy. Spark lo maneja bien, Tableau lo parsea bien, y tu equipo de infraestructura no te maldice.

Si tu Hive es moderno (3.x+) y usas exclusivamente Spark SQL, puedes cambiarlo a `DATE`. Pero no te lo recomiendo hasta que hayas probado el pipeline completo.

###### 2. `partitionOverwriteMode = 'dynamic'`

Esto es no negociable. Si un día falla el `mecv_production_runner` y necesitas re-procesar solo el `information_date = '2025-10-15'` para el `model_id = '1079_cta_lvl'`, el modo dinámico te permite sobrescribir esa partición sin tocar las otras 364 del año. Sin esto, cada reintento es un borrón total.

###### 3. Por qué NO particioné por `model_id`

Consideré `PARTITIONED BY (information_date, model_id)`. El problema: si tienes 200 modelos, cada `information_date` genera 200 subdirectorios en HDFS. Para una tabla que puede crecer a millones de filas, eso es manejable. Pero para `mecv_execution_log`, donde cada modelo genera una fila por día, 200 particiones con 1 fila cada una es un insulto al filesystem distribuido.

**Alternativa si el volumen explota:** Añade `CLUSTERED BY (model_id) INTO 256 BUCKETS` a `mecv_metric_result_d_t_d`. Los buckets son archivos dentro de la partición, no subdirectorios, y Spark los lee en paralelo eficientemente. Tableau ni se entera.

###### 4. Las vistas `mecv_dashboard_*`

No son tablas. No duplican datos. Son joins pre-cocinados para que el analista de Tableau no tenga que descubrir que `mecv_metric_result` se une con `mecv_alert_aggregate` por tres columnas. Si tu Tableau es lento, materializas la vista como tabla diaria en un DAG separado. Pero empieza con la vista.

##### Cambios Clave para Parquet Puro

###### 1. Particionamiento de Dos Niveles

Sin transacciones, `INSERT OVERWRITE` dinámico es tu única arma. Pero si particionas solo por `information_date`, re-procesar un modelo borra los datos de los otros 199 modelos de ese día. Por eso:

| Tabla | Partición Nivel 1 | Partición Nivel 2 |
|-------|-------------------|-------------------|
| `mecv_metric_result_d_t_d` | `information_date` | `model_id` |
| `mecv_alert_aggregate_d_t_d` | `information_date` | `model_id` |
| `mecv_execution_log_d_t_d` | `information_date` | `model_id` |
| `mecv_email_log_d_t_d` | `information_date` | `model_id` |
| `config_changelog_d_t_d` | `process_date` | `model_id` |
| `category_baseline_rank_d_t_d` | `process_date` | `model_id` |
| `metric_threshold_auto_d_t_d` | `process_date` | `model_id` |

Así, `INSERT OVERWRITE` dinámico solo toca el subdirectorio `information_date=2025-10-15/model_id=1079_cta_lvl/`. Los demás modelos de esa fecha no se ven.

###### 2. Tabla de Staging: `mecv_staging_control_d_t_d`

Sin metadata, necesitamos un registro de escrituras pendientes. Si el job muere entre "escribí en tmp" y "moví a producción", esta tabla dice dónde está el cadáver.

```sql

    staging_id              STRING      COMMENT 'UUID de la operación de staging',
    execution_id            STRING      COMMENT 'UUID de la ejecución del DAG',
    model_id                STRING      COMMENT 'Identificador del modelo',

TBLPROPERTIES (
```

###### 3. Protocolo de Escritura Atómica (Spark)

Tu DAG de producción debe seguir este patrón para cada tabla de salida:

```python
#### Paso 1: Escribir a temporal con co-locación de particiones
temp_path = f"/tmp/mecv/staging/{target_table}/{information_date}/{model_id}_{execution_id}"

df.write \
    .mode("overwrite") \
    .partitionBy("information_date", "model_id") \
    .parquet(temp_path)

#### Paso 2: Validar (contar filas, verificar schema, samplear calidad)
row_count = spark.read.parquet(temp_path).count()

#### Paso 3: Registrar en staging_control como VALIDATED
spark.sql(f"""
    INSERT INTO mecv_staging_control_d_t_d
    VALUES ('{staging_id}', '{execution_id}', '{model_id}', '{target_table}',
            '{information_date}', '{temp_path}', '{final_path}', {row_count},
            NULL, 'VALIDATED', current_timestamp(), current_timestamp(), NULL)
""")

#### Paso 4: Promover (swap)
#### En HDFS: fs.rename(temp_path, final_path) es atómico a nivel de directorio
#### En S3: copy + delete (no atómico, pero con staging_control puedes detectar huérfanos)

#### Paso 5: Registrar como PROMOTED y refrescar metadatos de Hive
spark.sql(f"MSCK REPAIR TABLE {target_table}")
spark.sql(f"""
    UPDATE mecv_staging_control_d_t_d
    SET status = 'PROMOTED', promoted_at = current_timestamp(), row_count_final = {row_count}
    WHERE staging_id = '{staging_id}'
""")
```

> **Nota sobre S3:** `rename` no es atómico en S3. Si usas S3, el protocolo cambia: escribes directo al path final con `information_date=X/model_id=Y/` pero usando un `execution_id` como sufijo en el nombre de archivo, luego haces un `INSERT OVERWRITE` de Hive que lee solo los archivos más recientes. O migras a HDFS para esta tabla crítica.

###### 4. Tabla de Huérfanos: Limpieza Periódica

Un DAG semanal (`mecv_orphan_cleanup`) lee `mecv_staging_control` donde `status = 'FAILED'` o `PROMOTED` con más de 7 días, y borra los paths temporales. Evita que `/tmp/mecv/staging/` crezca infinitamente.

##### Agujero que aún queda

**¿Están en HDFS o en S3?** Si es HDFS, `fs.rename()` de directorio es atómico y este protocolo es seguro. Si es S3, no lo es: entre el `copy` y el `delete`, otro job podría leer datos a medias. En S3 necesitarías:
- Escribir con `information_date=X/model_id=Y/` directamente (sin tmp), pero usando nombres de archivo con `execution_id` como prefijo.
- Hacer `INSERT OVERWRITE` en Spark que sobrescriba la partición completa (que ya es solo ese modelo-fecha gracias a las 2 particiones).
- Aceptar que si el job muere a mitad, la partición queda con archivos viejos y nuevos mezclados hasta el próximo re-proceso.

##### Protocolo de Escritura Atómica: Código de Referencia

Este es el patrón que cada tarea de Spark en los DAGs 2, 3 y 4 debe seguir al escribir a cualquier tabla de salida.

```python
from pyspark.sql import SparkSession, DataFrame
from pyspark.sql.functions import current_timestamp, lit
import uuid
from datetime import datetime

class AtomicParquetWriter:
    """
    Escritura atómica a Parquet sobre HDFS usando patrón staging + swap.
    Asume HDFS (fs.rename de directorio es atómico).
    """
    
    def __init__(self, spark: SparkSession, base_tmp_path: str = "/tmp/mecv/staging"):
        self.spark = spark
        self.base_tmp_path = base_tmp_path
        self.fs = spark._jvm.org.apache.hadoop.fs.FileSystem.get(
            spark._jsc.hadoopConfiguration()
        )
    
    def write_atomic(
        self,
        df: DataFrame,
        target_table: str,
        model_id: str,
        information_date: str,
        execution_id: str,
        partition_cols: list = None
    ) -> dict:
        """
        Escribe un DataFrame atómicamente a una tabla particionada.
        
        Returns:
            dict con {staging_id, temp_path, final_path, row_count, status}
        """
        staging_id = str(uuid.uuid4())
        temp_path = f"{self.base_tmp_path}/{target_table}/{information_date}/{model_id}_{execution_id}_{staging_id}"
        final_path = f"/user/hive/warehouse/{target_table}/information_date={information_date}/model_id={model_id}"
        
        # 1. ESCRIBIR A TEMPORAL
        # Co-locar particiones para evitar shuffle innecesario
        writer = df.write.mode("overwrite").option("compression", "snappy")
        
        if partition_cols:
            writer = writer.partitionBy(*partition_cols)
        
        writer.parquet(temp_path)
        
        # 2. VALIDAR
        temp_df = self.spark.read.parquet(temp_path)
        row_count = temp_df.count()
        
        # Sanity checks mínimos
        assert row_count > 0, f"Staging {staging_id}: 0 filas escritas"
        assert len(temp_df.columns) > 0, f"Staging {staging_id}: schema vacío"
        
        # 3. REGISTRAR EN STAGING CONTROL (status = VALIDATED)
        self._log_staging(
            staging_id=staging_id,
            execution_id=execution_id,
            model_id=model_id,
            target_table=target_table,
            information_date=information_date,
            temp_path=temp_path,
            final_path=final_path,
            row_count_temp=row_count,
            status="VALIDATED"
        )
        
        # 4. PROMOVER (Swap atómico en HDFS)
        # Borrar partición final existente (si hay)
        final_path_jvm = self.spark._jvm.org.apache.hadoop.fs.Path(final_path)
        if self.fs.exists(final_path_jvm):
            self.fs.delete(final_path_jvm, True)  # recursive=True
        
        # Mover temporal a final (ATÓMICO en HDFS)
        temp_path_jvm = self.spark._jvm.org.apache.hadoop.fs.Path(temp_path)
        success = self.fs.rename(temp_path_jvm, final_path_jvm)
        
        if not success:
            raise RuntimeError(f"fs.rename falló: {temp_path} -> {final_path}")
        
        # 5. REGISTRAR COMO PROMOTED
        self._update_staging_status(staging_id, "PROMOTED", row_count)
        
        # 6. REFRESCAR METADATOS DE HIVE
        self.spark.sql(f"MSCK REPAIR TABLE {target_table}")
        
        return {
            "staging_id": staging_id,
            "temp_path": temp_path,
            "final_path": final_path,
            "row_count": row_count,
            "status": "PROMOTED"
        }
    
    def _log_staging(self, **kwargs):
        """Inserta registro inicial en mecv_staging_control_d_t_d."""
        control_df = self.spark.createDataFrame([{
            **kwargs,
            "row_count_final": None,
            "started_at": datetime.now(),
            "validated_at": datetime.now(),
            "promoted_at": None,
            "process_date": datetime.now().strftime("%Y-%m-%d")
        }])
        control_df.write.mode("append").insertInto("mecv_staging_control_d_t_d")
    
    def _update_staging_status(self, staging_id: str, status: str, row_count_final: int):
        """Actualiza status en staging_control. En producción usar MERGE o DELETE+INSERT."""
        self.spark.sql(f"""
            INSERT OVERWRITE TABLE mecv_staging_control_d_t_d
            SELECT 
                staging_id, execution_id, model_id, target_table,
                information_date, temp_path, final_path, row_count_temp,
                {row_count_final} as row_count_final, '{status}' as status,
                started_at, validated_at, current_timestamp() as promoted_at,
                process_date
            FROM mecv_staging_control_d_t_d
            WHERE staging_id = '{staging_id}'
        """)
```
